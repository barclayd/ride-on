# Map prototype (MapLibre GL JS)

A browser prototype of the cycle.travel-style map that [the plan](../README.md) ports to the app. It's
where the style is compared against cycle.travel: the screenshots in [`../screenshots`](../screenshots)
were taken from it. Since WS2.1 its style comes from the production builder,
[`maps/style/`](../../../maps/style/README.md), so every rule in
[`cycle-travel-style.md`](../cycle-travel-style.md) is in `maps/style/src/style.ts` and the prototype
shows what the app draws, route badges included: both read the app's sprite (WS2.4).

It is **not** production code, but its data and style are: the basemap and the GB cycling overlay that
[`maps/tiles/`](../../../maps/tiles/README.md) builds (WS1.2), from `https://maps.ride-on.cc`, the same
archives the app reads.

## What's here

| Path | What it is |
|---|---|
| `index.html` | MapLibre GL JS page. Loads `style.json`, registers the `pmtiles://` protocol, sets `window.map` for the capture scripts |
| `style.json` | Generated by `maps/style`'s `web` target (95 layers, `bun run style`). Committed so the style can be read without running anything. Tiles from `https://maps.ride-on.cc`, glyphs and sprite from `http://localhost:8787` |
| `tools/serve.ts` | Bun static server on :8787 with byte ranges (for archives in `data/`), plus the app's files from `app/Packages/Features/Sources/RoutesUI/CycleMap/`: `/glyphs/` (Montserrat glyph PBFs) and `/sprite` (the badge images) |
| `scripts/setup-vendor.sh` | Copies the MapLibre and PMTiles browser builds out of `node_modules` into `vendor/` |
| `overpass/park.overpass` | Every highway in Richmond Park, the input to `analysis/ct-classify.py` (how the path rule was worked out) |
| `capture/` | Scripts for Chrome DevTools `evaluate_script`: `ct-prep.js` hides cycle.travel's sidebar and waits for tiles, `ct-phone-prep.js` does the same for its mobile site, `ml-prep.js` waits for the prototype. `ml-headless.mjs` captures the prototype headless; `app-sim.sh` captures the app in the iOS Simulator |
| `analysis/` | Python measuring tools used to tune the style against cycle.travel screenshots (table below) |

`vendor/`, `node_modules/` and `data/` are gitignored.

## Run it

Needs Bun (≥1.4). From this directory:

```sh
bun install
bun run setup                              # vendor/ from node_modules
(cd ../../../maps/style && bun install)    # the style builder
bun run style                              # style.json (after editing maps/style/src/style.ts)
bun run serve                              # http://localhost:8787
```

Open `http://localhost:8787/#13/51.4455/-0.2665` (MapLibre's hash is `#zoom/lat/lon`). After rebuilding
the style, reload with the cache disabled: the browser holds on to `style.json`.

`style.json` reads both archives from `https://maps.ride-on.cc`, whose CORS rules allow any origin.
To work offline or try a new build, put the files named in `maps/style/src/style.ts`'s `archives`
(`basemap-gb-<date>.pmtiles`, `cycling-gb-<date>.pmtiles`) in `data/` (symlinks work) and run
`bun run style:local`; run `bun run style` again before committing. Building the overlay needs Docker:
see [`maps/tiles/`](../../../maps/tiles/README.md). The basemap is Ride On's GB extract of a Protomaps
build (plan WS1.1).

Both cover Great Britain (Geofabrik's `united-kingdom` extract also has Northern Ireland). Outside it the
map is blank.

**Overpass.** Until WS1.2 the cycling layers came from Overpass as GeoJSON for south-east England; that
pipeline is gone. `park.overpass` is the only query left, for the analysis tools: send it to
`https://overpass-api.de/api/interpreter` with User-Agent `ride-on-map-prototype/0.1`, and back off on
502/504.

## Comparing against cycle.travel

The screenshots were taken with the Chrome DevTools MCP server. The method, so new ones line up:

1. `emulate` a 1200×800 viewport at device pixel ratio 2 (not `resize_page`).
2. cycle.travel: navigate to `https://cycle.travel/map?lat=<lat>&lon=<lon>&zoom=<ct zoom>`, run
   `capture/ct-prep.js` with `evaluate_script`, take the screenshot.
3. Prototype: navigate to `http://localhost:8787/#<ct zoom − 1>/<lat>/<lon>`, run `capture/ml-prep.js`,
   take the screenshot. Don't wait on `map.once('idle')` from `evaluate_script`: it hangs. The script polls
   `map.loaded() && map.areTilesLoaded()` instead.
4. `analysis/pair2.py ct.png ml.png out.jpg 350 1`. cycle.travel's map still lays out as if the sidebar
   were there, so its features sit 350 device px to the right of ours; the script crops that off.

**Running the MCP.** `~/.mcp.json` runs `chrome-devtools-mcp --autoConnect`, which attaches to Dan's own
Chrome: open your own tabs with `new_page`, never navigate his. A Claude Code background job may fail to
attach ("Could not find DevToolsActivePort": macOS privacy controls stop the daemon reading Chrome's port
file); a foreground terminal session attaches fine. The MCP only reads and writes files inside the
session's workspace roots, so pass `capture/*.js` to `evaluate_script` inline.

**Headless prototype captures.** `bun capture/ml-headless.mjs <outDir> [view ...]` captures the prototype
for the ten comparison views in headless Chrome, with no MCP needed. Headless Chrome renders colours
slightly differently from a display tab, and cycle.travel returns 403 to it, so cycle.travel's side still
comes from a display Chrome (steps 1–2). Map the headless colours to that display's before pairing:
`analysis/lut.py apply analysis/lut-srgb.json ml.png ml-disp.png`. `lut-srgb.json` was fitted
(`lut.py fit`) on headless and display captures of the same views on the sRGB display; 94–98% of pixels
land within 2/255, and geometry is identical. Refit it on any other display.

**Phone comparisons (3×).** The `phone-*.jpg` trios compare cycle.travel's mobile site, the app and the
prototype in the window the Routes map shows above the panel at its medium detent on an iPhone 17:
402×299 pt at 3×, 1206×897 px. For each of the ten views:

1. cycle.travel: in a display Chrome, `emulate` the viewport `402x299x3,mobile,touch`, navigate to
   `https://cycle.travel/map?lat=<lat>&lon=<lon>&zoom=<ct zoom>`, run `capture/ct-phone-prep.js` (inline)
   and take the screenshot. Its mobile map has no sidebar, so there is no `dx`. At 3× it draws its 2×
   tiles scaled 1.5×, so its lines and dots are a touch soft.
2. App: build Ride On for the Simulator, install it, then
   `sh capture/app-sim.sh <udid> <outDir> [view ...]`. It launches `--fixture-world --cycle-map
   -CycleMapCamera <lat,lon,zoom>` per view and crops the map window once two screenshots a second apart
   match. Use the iPhone 17 simulator `79662D65-4914-46BC-BA2A-510E3989498D`, never `booted`.
3. Prototype: `bun capture/ml-headless.mjs --phone <outDir> [view ...]`, which hides GL JS's controls.
   The trios leave its colours as captured; they're for sizes and placement, not colour.
4. `analysis/trio.py ct.png app.png ml.png out.jpg`.

The app captures keep its map controls (the layers and location buttons, the attribution `i`).
Measure text with `ink.py` over the same label on each side: `dotsize.py` and
`badges.py` assume DPR 2 colours and sizes and don't work on these.

**Zoom offset.** cycle.travel is Leaflet with 256 px tiles; MapLibre uses 512 px tiles. cycle.travel zoom
*n* is MapLibre zoom *n − 1*. Every zoom in the style doc is given in MapLibre zooms unless it says "ct".

The screenshots are only for comparison. Don't scrape or proxy cycle.travel's tiles or APIs (its tile
server returns 403 to non-browser clients, and that's their call).

## Analysis tools

Python 3.12+: `python3 -m venv analysis/.venv && analysis/.venv/bin/pip install -r analysis/requirements.txt`.
Run them with `-I` and paths as arguments. All measurements are in device pixels of a DPR 2 screenshot, or DPR 3 for the phone captures.

| Tool | Use |
|---|---|
| `pair.py`, `pair2.py` | Side-by-side comparison images |
| `crop.py` | The same crop from several images, upscaled, side by side |
| `sheet.py` | Contact sheet of labelled crops (uses macOS Helvetica) |
| `dots.py image colour` | Diameter and spacing of route dots of one colour |
| `dashes.py` | Length, width and spacing of brown unpaved dashes. Crashes if it finds fewer than two dashes |
| `badges.py`, `shield.py` | Find route badges and measure their box and colours |
| `ink.py` | Bounding box of dark text pixels, for label size and letter-spacing |
| `ct-classify.py`, `overlay.py` | For each OSM way in an Overpass dump, which cycle.travel line style is drawn under it; draw ways over a screenshot. How the path rule was worked out |
| `calib.py`, `calib2.py` + `cal.json` | Fit the screenshot colour transform behind `shot()` (`maps/style/src/shot.ts`) from a page of 80 known swatches |
| `near.py`, `sample.py`, `topcols.py` | Colour sampling helpers |
| `crop2.py` | The same box (in prototype device px) from a cycle.travel and a prototype capture, side by side |
| `greyruns.py` | Modal colour and width of thin grey lines in a box: minor roads and streets |
| `perp.py`, `prof.py` | A line's width, or its raw RGB, along perpendicular profiles at a given point and angle |
| `lanes.py`, `lanes2.py` | Line width and darkness, prototype vs cycle.travel, at a list of points; `lanes2.py` groups by road kind |
| `abprof.py` | Profiles across Colchester's A133 and B1027 at several zooms: casing, fill and width against cycle.travel |
| `dotsize.py` | Diameters of red route dots |
| `lut.py` + `lut-srgb.json` | Fit and apply a per-channel colour curve from headless captures to a display's |
| `runw.py` | Run lengths of A-road (pink) and B-road (orange) fill, i.e. road fill widths |
| `trio.py` | The phone comparison: cycle.travel's mobile site, the app and the prototype side by side at 3× |

The tools that compare two captures take `dx`, cycle.travel's horizontal offset in device px. It is 350
with the method above; the batch D Colchester captures needed 342. Check it with `crop2.py` before
trusting a measurement.
